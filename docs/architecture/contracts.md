# Каталог контрактов

| | |
|---|---|
| Версия | 1.0, 22.10.2026 |
| Решение | ADR-014: схемы пишутся в коде (zod) в `packages/shared/contracts`, из них генерируются OpenAPI и JSON Schema |
| Связано | словарь данных `docs/architecture/data-dictionary.md`, спецификация разделы 7.4, 7.5 |

## 1. Зачем

Контракт это договор между частями системы: что приходит, что уходит, в
каком виде. Пока контракт не меняется, части можно переписывать
независимо. Для Сары это особенно важно: части пишут разные сессии Claude
Code, и единственное, что их связывает, это контракты и тесты.

## 2. Правила для всех контрактов

- **Один источник правды:** схема zod в `packages/shared/contracts/<имя>.ts`.
  OpenAPI для пульта и JSON Schema для ролей и MCP генерируются из неё в
  CI и не правятся руками.
- **Версия:** у каждого контракта номер версии. Добавить необязательное
  поле можно без новой версии. Удалить, переименовать, сделать
  обязательным: только новая версия и ADR.
- **Тесты контракта:** у каждого контракта есть образцы (настоящие или из
  калибровки) и тест, что образцы проходят схему, а код разбирает их без
  потерь.
- **Время** всегда ISO 8601 в UTC; деньги целым числом в рублях; номера
  заказов Профи.ру строкой.

## 5. C2. Профи-MCP

**Инструменты** (`profi.*`). Все принимают `account_id`. Изменяющие
инструменты принимают `idempotency_key` и `permit` (подпись ядра, что
правила проверены).

| Инструмент | Вход | Выход | Меняет площадку |
|---|---|---|---|
| `session_health` | | жива ли сессия, баланс, присутствие, IP | нет |
| `list_feed` | фильтр, с какого времени | список заказов: номер, тема, город, бюджет, цена отклика, время | нет |
| `get_order` | номер заказа | заказ целиком со страницы: открыт ли, есть ли уже наш отклик, цена отклика сейчас, имя клиента и текст, если доска их не дала, и сведения о клиенте (`client_info`: с какой даты на Профи.ру, номер подтверждён, отзывы и их теги). Ядро зовёт его только для заявки, которую пропустил Оценщик | нет |
| `list_chats` | с какого времени | чаты: номер, заказ, клиент, последнее сообщение, непрочитано | нет |
| `read_chat` | номер чата | сообщения с номером площадки, автором, временем, «прочитано» | нет |
| `submit_bid` | номер заказа, текст, цена услуги, предел цены отклика (`max_fee_rub`), срок нажатия (`not_after`), ключ, разрешение | отклик найден на странице или нет, трата, баланс | да |
| `send_message` | номер чата, текст, последнее сообщение, которое видело ядро, ключ, разрешение | сообщение найдено на странице: да, и его номер площадки | да |
| `backfill_chats` | период | выгрузка истории порциями | нет |

**Уведомления** (Профи-MCP → ядро): `order_seen`, `order_changed`,
`client_message`, `client_typing`, `client_read`, `chat_closed`,
`session_dead`, `profile_banned`, `layout_changed`, `balance_changed`.

Добавлено в M1: `session_alive` (вход снова жив, с временем, когда умер),
`author_unclear` (автор сообщения не определён, действий по чату нет),
`connection_lost` и `connection_back` (площадка недоступна дольше 30
минут и снова доступна). В событиях о сообщениях нет текста клиента:
только номера, время и автор (ADR-022); текст лежит в схеме `node`.

**Классы ошибок:** `SESSION_DEAD`, `BANNED`, `LAYOUT_CHANGED`,
`NOT_FOUND`, `ORDER_CLOSED`, `NO_MONEY`, `UNSAFE_PAYMENT` (площадка просит
оплату не с кошелька), `PRICE_CHANGED` (отклик стоит дороже `max_fee_rub`),
`RATE_LIMITED`, `UNCERTAIN` (действие могло пройти, нужна проверка),
`INTERNAL`, `CHAT_CHANGED` (M4: в чате новое сообщение, которого ядро не
видело; ничего не набрано). Для отклика любой класс, кроме `UNCERTAIN`,
значит: отклик не нажат.

**M4.** Инструмент `profi.send_message` (аккаунт, чат, текст,
`expect_last_message_id`, ключ от повтора, разрешение → найдено ли на
странице, номер сообщения): служба читает живую страницу перед набором и
отказывает `CHAT_CHANGED`, если последнее сообщение не то, что видело ядро.
Разрешение на сообщение (`signMessagePermit`) подписывает аккаунт, чат,
хеш текста и ключ: оно не годится ни для другого текста, ни для отклика.
События `specialist_message` (новое сообщение нашей стороны, без текста),
`client_typing`, `client_read`.

**Живая отправка (`src/chat/sendTools.ts`).** Выключена, пока на службе не
задано `SARA_NODE_SEND_MESSAGES=1`: тогда новый ключ получает `INTERNAL`
«отправка сообщений выключена на службе», страница не открывается, ничего
не записывается. Включённая работает так:

1. Проверяет разрешение (`INTERNAL`, если не подходит). Ключ, который служба
   уже видела, отвечает первым и без отказов: записанный итог возвращается
   из базы даже при выключенной отправке и умершей сессии; ключ, чьё нажатие
   записано, а ответа нет (служба упала после нажатия), при выключенной
   отправке или умершей сессии даёт `UNCERTAIN` без открытия браузера, иначе
   только смотрит чат: свой новый пузырь с этим текстом после последнего
   сообщения, которое видело ядро, даёт ответ, иначе `UNCERTAIN`. Ключ,
   записанный для другого чата или аккаунта, даёт `INTERNAL`, не чужой итог.
   Итог ключа лежит в `node.message_attempt` и переживает перезапуск.
2. Для нового ключа отказывает текст, похожий на служебный (JSON, тег
   `parameter`), как это делала старая Сара, и умершую сессию
   (`SESSION_DEAD`, `BANNED`).
3. Встаёт в очередь вкладки аккаунта, как остальная работа на странице. Если
   вкладка занята дольше 150 секунд: `UNCERTAIN` (ничего не набрано, но ядро
   сначала читает чат, потом решает). Вкладка не ходит на сайт (живой экран,
   связь, IP) или ядро положило трубку: `RATE_LIMITED`, ничего не набрано.
   Срок нажатия считается от прихода вызова (4 минуты ожидания ядра минус
   проверка после нажатия и полминуты): позже служба ничего не нажимает и
   отвечает `UNCERTAIN`, набранное стирается. Набор проверяет это и то, что
   ядро не положило трубку, между кусками текста.
4. Открывает чат как старая Сара (`r.php?id=<номер чата>`) и требует, чтобы
   вкладка стояла на адресе именно этого чата (иначе `NOT_FOUND`, а при
   умершей сессии `SESSION_DEAD`): ничего с чужой страницы не читается и не
   доходит до глаз. Читает чат дважды с паузой, пока два чтения не совпадут.
5. Страница читается не так: нет ни одного сообщения, хотя ядро видело
   сообщения, есть сообщение неизвестной стороны, у сообщений нет слов, нет
   поля `textarea[placeholder="Сообщение"]` или кнопки отправки рядом с ним
   (последняя кнопка третьего предка `div` поля) или кнопка не изменилась
   после набора (возможно, это микрофон): `LAYOUT_CHANGED`. Последнее
   сообщение не то, что видело ядро (`null` значит «чат пуст», его служба
   ждёт дольше): `CHAT_CHANGED`, ничего не набрано; увиденное служба сразу
   отдаёт глазам, как обычная сверка чатов.
6. Набирает текст в поле человеческим темпом (переносы строк вставкой
   текста, не клавишей Enter), читает поле обратно; не принявшее текст целиком
   поле даёт `INTERNAL`, черновик стирается. Прямо перед записью нажатия чат
   читается ещё раз: если за время набора он изменился (клиент дописал, Борис
   ответил) или поле опустело, это `CHAT_CHANGED`, черновик стирается.
   Нажатие записывается в `node.message_attempt` до кнопки.
7. После нажатия сообщением считается только новый пузырь нашей стороны с
   этим текстом, без знака отправки или отказа, который вторым чтением через
   1-2 секунды всё ещё стоит под тем же номером: `{found_on_page: true,
   platform_message_id}`. Не появился за 15 секунд, пропал или остался
   «отправляется»: `UNCERTAIN`, повторов вслепую нет. Любой сбой после записи
   нажатия тоже `UNCERTAIN`; до записи это `INTERNAL`, сообщение не ушло.
   Если сохранить итог не удалось, ответ всё равно `found_on_page: true`, а
   повтор ключа найдёт то же сообщение. Запросы страницы после нажатия (способ,
   адрес без чисел, статус, без тел) пишутся в `node.raw_event`
   (`what: chat_send`) для калибровки; ответу площадки служба пока не верит,
   потому что его адрес и вид не известны.

Первая выкладка записывает форму сообщения (поле, кнопки, вложения, без
текстов) один раз в `node.raw_event` (`what: chat_form`), и ещё раз, уже с
набранным текстом, при первой отправке (`typed: true`), чтобы проверить
селекторы без нажатий.

**Отклик (с 25.10.2026).** Разрешение ядра подписывает ключ, номер заказа,
`max_fee_rub` и `not_after` вместе. `max_fee_rub` это цена отклика на
карточке, на которую нажал Борис: служба не платит больше, ни по ответу
страницы, ни по подвалу формы («К оплате»). `not_after` ставит ядро: за
полминуты до конца своего ожидания (4 минуты). После этого срока, и когда
ядро положило трубку (запрос отменён), служба ничего не нажимает. Нажатие
записывается до кнопки, которая открывает форму (`node.bid_attempt`), поэтому
повтор с тем же ключом только смотрит; остановка до «Откликнуться» стирает
запись, только если кошелёк на странице не изменился.

## 6. C3. Роли модели

Каждая роль лежит в `roles/<роль>/` и состоит из:

| Файл | Что |
|---|---|
| `role.md` | инструкция роли (статичная часть, кэшируется) |
| `schema.json` | JSON Schema ответа (генерируется из zod) |
| `meta.json` | модель, запасная модель, приоритет, `max-turns`, тайм-аут, версия |
| `evals/` | образцы входа с ожидаемым ответом для проверки роли |

**Пример: Сортировщик, версия 0.**

```json
{
  "verdict": "fit | maybe | reject",
  "reason": "строка до 200 знаков, по-русски",
  "tags": ["маркетинг", "сайт"],
  "confidence": 0.0
}
```

Правило: ответ без `structured_output` или не по схеме это сбой шлюза,
один повтор, затем черновик Борису (дизайн v3, раздел 20.2).

**M5.** Роли школы (схемы в `packages/shared/src/contracts/school.ts`):
`trainer-client` (haiku, P1, `TrainerClientOutput`), `trainer-coach`
(sonnet, P1, `CoachOutput`), `lesson-maker` (haiku, P3 ночью и P1 в
тренажёре, sonnet для интервью, `LessonMakerOutput`), `teacher` (opus, P3,
`TeacherOutput`), `persona-builder` (sonnet, P3, `PersonaOutput`),
`dialog-generator` (sonnet, P3, `GeneratorOutput`). Номер записи из
ответа модели только по `MIND_RECORD_ID`; файл записи собирает код.

## 7. C4. API пульта

Ресурсы по вещам карты сущностей, одна вещь = один ресурс, все под
`/api` (уточнено дизайном M7, `docs/superpowers/specs/2026-10-25-m7-pult-design.md`,
раздел 6):

`/accounts`, `/directions/{accountId}`, `/leads`, `/clients` (Клиент:
разговор M4 и его сделка; заменяет `/deals`), `/clients/{id}` с перепиской,
`/conversations/{id}/take|return|say|close` (команды M4), `/meetings`
(M6: список, отметка, `/meetings/{id}/outcome`, `/meetings/availability`),
`/tasks/{id}/{action}`, `/questions/{id}/answer`, `/inbox` (сборка задач
и вопросов, ничего не хранит), `/today` (сборка для экрана «Сегодня»),
`/mind`, `/lessons`, `/trainings`, `/exams`, `/analytics/funnel|speed|load`
(M6), `/settings`,
`/cutover`, `/search`, `/health`, `/journal` (события C1; заменяет
`/events`), `/journal/trace/{correlationId}`, `/setup`, `/screen/ticket`.

- Живые обновления: `GET /api/stream` (SSE), кадры `{type, kind, id, at}`
  из C1 без данных клиентов, пульт перечитывает открытые экраны; при потоке
  опрос раз в 60 секунд, без потока раз в 20 секунд (пульт v2,
  `docs/superpowers/specs/2026-10-29-pult-v2.md`).
- Колокольчик: `GET /api/notices?state=new|open|all`, `POST /api/notices/seen
  {ids}`, `POST /api/notices/{id}/done`; схема `NoticeList` в
  `packages/shared/src/contracts/inbox.ts`. Входящие: `GET /api/inbox`
  (`InboxView`), вопрос Сары `POST /api/questions/{id}/answer {text}` и
  `/skip`. Журнал `JournalView`, трасса `TraceView`, поиск `SearchView`
  в `packages/shared/src/contracts/journal.ts`.
- Заявки (пульт v2): `GET /api/leads?order=combined|fit|chance`, балл двумя
  числами `LeadScores` («Насколько наше», «Шанс дойти до денег», сочетание,
  `combinedScore`); `POST /api/leads/{id}/bid {expectedFeeRub}` ставит
  отклик с отсрочкой 10 секунд, `/bid/cancel` отменяет, `/skip {reason?}`,
  `/recheck` перечитывает заказ.
- Клиенты (пульт v2): `GET /api/clients` (`ClientList`), `GET /api/clients/{id}`
  (`ClientView`: этап, переписка, открытые задачи клиента, встречи, итог),
  `POST /api/clients/{id}/note {text}`, `POST /api/clients/{id}/outcome
  {outcome: won|lost|null, amountRub, reason, service}`; встречи
  `GET|POST /api/meetings`, `POST /api/meetings/{id}/outcome {outcome,
  amountRub}`. Прежние `GET /api/conversations` убраны, команды M4
  `POST /api/conversations/{id}/take|return|say|close` остаются.
- Вход: пароль владельца (сессия в cookie) или подпись Telegram Mini App
  в заголовке `Authorization: tma <initData>` на каждом запросе (проверка
  подписи токеном бота, возраста до 24 часов и номера пользователя);
  WebSocket живого экрана входит одноразовым билетом `/api/screen/ticket`.
- Ключи переключения (`PROTECTED_KEYS`) меняются только через `/cutover`.
- Схема: `GET /api/openapi.json`, строится из схем zod пульта
  (`packages/shared/src/contracts/pult.ts`, `z.toJSONSchema`).

## 8. C5. Кнопки Telegram

Формат `callback_data`: `t:<номер задачи>:<действие>`, до 64 байт.
Действия: `bid`, `edit`, `skip`, `send`, `take`, `return`, `done`,
`move`, `open`, `want`, `apply`, `drop`, `good` (M4: «Хорошо» на
черновике разговора), `close` (M4: «Закрыть» разговор и задача «Клиент
молчит после трёх напоминаний»), `all` (M5: «Все да» под пачкой уроков); на
карточке напоминания «Отправить», «Изменить» и «Не надо» это `send`, `edit`
и `skip`. Действия `remind` («Напоминать дальше») больше нет. Нажатие по
решённой задаче отвечает «уже сделано» и
ничего не меняет.

## 9. C6. Файлы разума

Поля сверху каждого файла:

| Поле | Значения |
|---|---|
| `id` | постоянный номер записи |
| `type` | `knowledge`, `understanding`, `speech`, `judgment`, `example` |
| `scope` | `shared` или номер направления |
| `status` | `confirmed`, `proposal`, `outdated` |
| `version` | число |
| `sources` | откуда (правка, тренировка, интервью, история) |
| `valid_from`, `valid_to` | срок действия |

Версия 2 (M4), необязательные поля: `title`, `tags`, `topic` (тема
самостоятельности), `tones` (тон клиента), `stages` (этапы разговора),
`examples` (номера образцов). `id` уникален во всём разуме и начинается с
буквы типа: `k-`, `u-`, `s-`, `j-`, `e-`. Тело записи по типам: дизайн M4,
раздел 5.2. Ядро только читает клон `sara-mind`; предложения копятся в
`core.mind_proposal` и попадают в репозиторий через разработку.

**M5 (ADR-025).** После «да» Бориса писатель разума ядра собирает файл из
поля `change` предложения (или берёт `content` у предложений M4), проверяет
его и делает один коммит в свой клон от автора `Сара <sara@hance.local>`
со строками `Sara-Commit: <номер строки core.mind_commit>` и
`Sara-Proposals: <номера>` в конце сообщения; по ним база и git
сверяются после сбоя, а откат находит коммит. Ночью клон сливается с
`origin/main` (слиянием, без перебазирования) и отправляется в GitHub.
Номера записей из уроков: `e-l-<n>`, `k-i-<n>` по порядковому номеру
урока.

## 10. C7. Настройки

Каждая настройка: ключ, тип, значение по умолчанию, кто меняет, история
изменений. Значение из пульта важнее файла `.env` (урок v1). Список
ключей растёт по вехам и ведётся в `packages/shared/contracts/settings.ts`.
M5 добавляет `school.*` (ночная школа, пачки, бюджет в единицах, счёт
сообщений) и `auto.*` (повышение и понижение тем, исключение старта);
уровни тем остаются в `conv.autonomy` (M4).

Переключатели разговоров (M4), которые меняют, что уходит клиенту:

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `pipeline.conversations` | выключено | сообщения клиентов начинают ходы разговора |
| `conv.v1_writes` | включено (тень) | «Сара v1 пишет клиентам с этого аккаунта»: пока включено, новая Сара не отправляет ничего (ADR-024) |
| `outbound.messages` | выключено | пауза «Пишет клиентам»: держит собственные ответы и напоминания Сары; нажатие Бориса «Отправить» её тоже уважает, его собственный текст проходит |
| `conv.autopilot` | выключено | автопилот: пока выключен, Сара сама не отправляет клиенту ни ответ, ни напоминание; уходит только то, на что нажал Борис («Отправить», «Изменить») или что он написал сам. Это режим черновиков (RB-22); включается после экзамена и недели в тени |
| `conv.cards_per_day` | 10 | потолок карточек черновиков в день, только в тени; после переключения карточки не ограничены |

Ворота одни: `queueMessage` (`conversation/outbox.ts`). При выключенном
автопилоте сообщение автора `sara` проходит только с ключом `send:<номер
задачи карточки>`, если задача закрыта нажатием «Отправить».

## 11. C8. Доставка событий Профи-MCP

Служба Профи-MCP записывает событие в схему `node` (ADR-021, ADR-022),
затем доставляет его в ядро через свою очередь. Доставка
повторяется до подтверждения; ядро принимает событие с тем же `id` один
раз (ADR-019).

Уточнение после проверки M0: в журнал ядра (он только на добавление и
хранится годами) `profi.order_seen` попадает без `client_name` и `text`;
они хранятся в строке `lead` и удаляются по срокам. Повтор того же события
снова запускает обработку заказа: она защищена номером процесса
`lead:<номер заказа>`, поэтому сбой между записью в журнал и обработкой не
теряет заявку.
