## 0. Сводка на одну страницу

**Проблема.** Сара v1 за 42 дня: 4369 заявок, 26 откликов на 3277 ₽, 70%
клиентов ответили, 0 встреч, 0 известных договоров. Память теряется, итоги
не считаются, эксплуатация ручная, 41 находка аудита.

**Решение.** Новая Сара: один ИИ-сотрудник продаж на Профи.ру с разумом
по идее Бориса (знание, понимание, речь, суждение, память). Видит заявку и
приносит её Борису меньше чем за 2 минуты, после «да» откликается за
минуту, разговаривает голосом Бориса, договаривается о встрече, учится на
тренажёре и правках. Несколько аккаунтов разных направлений без
конкуренции. Один пульт: веб-приложение, Mini App, бот.

**Ключевые решения:**
1. Модель через Claude Code CLI по подписке, без API **[Б]** (ADR-001).
2. Профи.ру гибридно: события и данные сайта для чтения, интерфейс для
   действий, проверка экраном; всё за границей Профи-MCP (ADR-002, 003).
3. Два сервера: ядро за рубежом, узел Профи.ру в России с отдельным IP на
   аккаунт (ADR-004) **[П]**.
4. Данные: первичная запись в России, рабочая копия у ядра за рубежом,
   уведомление в Роскомнадзор (ADR-005) **[П]**.
5. Разум как git-репозиторий файлов, обучение без дообучения модели
   (ADR-007, 008).
6. Направления аккаунтов с системой оценки от Claude и маршрутизатор
   (ADR-009) **[Б]**.
7. Новый бот Telegram (ADR-010) **[П]**.
8. Без календаря, встречу отмечает Борис (ADR-012) **[Б]**.

**Метрики успеха:** заявка у Бориса меньше чем за 2 минуты; отклик меньше
чем за минуту после «да»; «ответил → созвон» от 25%; 60% ответов без
Бориса через два месяца; в слепом тесте Борис не отличает себя от Сары; 0
дублей и выдуманных фактов.

**Вехи:** M0 фундамент → M1 Профи-MCP → M2 заявки и отклик в одно
нажатие → M3 направления → M4 разум и разговор → M5 тренажёр и обучение
→ M6 встречи и итоги → M7 пульт и переключение с v1 → M8 второй
аккаунт.

## 1. Контекст

- **Площадка.** Профи.ру: клиенты публикуют заказы, специалисты платят за
  отклик (в маркетинге в среднем 192 ₽). Публичного API для специалистов
  нет.
- **Как площадка распределяет заказы** (справка Профи.ру): место отклика
  задаёт рейтинг анкеты; клиент видит отклики в порядке поступления; если
  заказ подходит многим, его сначала показывают тем, кто чаще
  договаривается. Значит, решают скорость и доля договорённостей.
- **v1** работает на сервере в Болгарии: демон с браузером, сессия Claude
  Code в Telegram, Mini App. Аудит нашёл 41 проблему: 12 критичных, 23
  важных, 6 мелочей.
- **Ресурсы:** подписка Claude, малый бюджет на серверы, разработка
  силами сессий Claude Code, Борис принимает решения и результат.

## 2. Цели, метрики, границы

### 2.1 Цели и как их мерить

| № | Цель | Метрика | Значение | Как мерится |
|---|---|---|---|---|
| G1 | Быть среди первых откликов | время от появления заявки до карточки у Бориса | меньше 2 минут у 90% заявок | журнал событий |
| G2 | Решение Бориса исполняется сразу | время от «да» до отклика в чате | меньше 60 секунд | журнал |
| G3 | Доводить до встречи | доля «клиент ответил → встреча назначена» | от 25% | когорты |
| G4 | Говорить как Борис | слепой тест: Борис отличает свой ответ | не лучше угадывания (около 50%) | тренажёр, раз в неделю |
| G5 | Снимать работу с Бориса | доля ответов клиентам без участия Бориса | 60% через два месяца после M5 | журнал |
| G6 | Знать деньги | цена ответа, встречи, договора по направлениям | считается каждый день | аналитика |
| G7 | Не ошибаться | дубли, выдуманные факты, потери данных | 0 | проверки, аудит журнала |

### 2.2 Не цели первой версии

Лора, Ultimate Hance, календарь, ссылки на видеовстречи, звонки голосом,
другие площадки, продажа коробки, дообучение весов модели.

### 2.3 Анти-цели

Провал, даже если «работает»: выдуманные факты; траты без решения Бориса;
поток уведомлений; два аккаунта на одном заказе; роботный тон; дубль или
ответ поверх ответа Бориса; потеря памяти после перезапуска.

## 3. Пользователи и сценарии

**Борис** (владелец, единственный пользователь пульта): решает про деньги
и клиентов, принимает работу Сары, учит её. Пишет коротко, с телефона и
компьютера. Нужен простой язык и одно сообщение вместо многих.

**Клиент Профи.ру** (внешний): видит только сообщения в чате площадки. Не
должен почувствовать робота.

| № | Сценарий («Когда…, хочу…, чтобы…») |
|---|---|
| JS-1 | Когда на площадке появилась подходящая заявка, хочу получить готовый отклик с кнопкой, чтобы откликнуться среди первых |
| JS-2 | Когда клиент ответил, хочу, чтобы Сара продолжила разговор моим голосом и звала меня только по моим темам |
| JS-3 | Когда клиент согласился на созвон, хочу узнать время и бриф, чтобы подготовиться |
| JS-4 | Когда Сара ответила не так, как я, хочу поправить один раз, чтобы она запомнила |
| JS-5 | Когда есть свободные 5 минут, хочу потренировать Сару на типовых клиентах |
| JS-6 | Когда завожу новый аккаунт, хочу описать направление словами и получить систему оценки, которой можно доверять |
| JS-7 | Когда что-то сломалось, хочу одно понятное сообщение и кнопку, что сделать |
| JS-8 | Когда открываю пульт, хочу за 10 секунд понять, что ждёт меня и сколько это приносит |
| JS-9 | Когда ставлю систему с нуля, хочу пройти шаги с инструкцией и проверкой |

## 6. Архитектура

### 6.1 Принципы

1. Одна Сара: один разум и одна память на все входы.
2. Один источник правды: журнал событий.
3. Модель предлагает, код решает: деньги, отправку, паузы проверяет код.
4. У аккаунта один владелец браузера: Профи-MCP.
5. Действия наружу через исходящую очередь с подтверждением.
6. Долгие процессы переживают перезапуск.
7. Неуверенность останавливает действие.
8. Всё измеряется.

### 6.2 Уровень 1: контекст (C4)

Сара связана с пятью внешними системами: Профи.ру (заказы и чаты),
Telegram (бот и Mini App), Claude (через CLI по подписке), почта Профи.ру
(резервный сигнал), хранилище бэкапов. Пользователь один: Борис. Клиенты
Профи.ру общаются с Сарой только через чат площадки.

### 7.2 Машина состояний клиента

Этапы: `found → queued → bid_sent → talking → call_proposed →
call_booked → call_done → won | lost`, плюс `dormant`. Владелец: `sara`,
`boris`, `paused`. Чей ход: `client`, `sara`, `boris`, `nobody`.
Эскалация меняет владельца, чат читается всегда. Каждый этап запускает
свои устойчивые процессы (напоминания, ожидания) и отменяет процессы
прошлого этапа.

### 7.3 Цикл ответа

Шаги: услышать → вспомнить → понять (смысл и тон) → сказать → проверить
→ правила → отправить → научиться. Таблица шагов, исполнителей и
поведения при сбое: дизайн v3, раздел 6.

### 7.4 Шлюз модели и роли

**Контракт вызова роли:**

```
claude -p --model <haiku|sonnet|opus> --fallback-model <запасная>
  --system-prompt-file roles/<роль>.md
  --append-system-prompt-file <контекст>.md
  --output-format json --json-schema <схема роли>.json
  --tools "" --strict-mcp-config
  --setting-sources project --permission-mode dontAsk --permission-prompts none
  --max-turns <N> --no-session-persistence
```

- Роли (11): Сортировщик, Оценщик и маршрутизатор, Аналитик, Собеседник,
  Проверяющий, Секретарь, Тренер, Онбординг направления, Учитель,
  Экзаменатор и генератор, Ремонтник вёрстки. Модели и инструменты: дизайн
  v3, раздел 12.1.
- Приоритеты: P0 клиенты, Борис, быстрые заявки; P1 отклики, тренажёр; P2
  лента; P3 учёба ночью.
- Параллельно 2 вызова; счётчик лимита в окнах 5 часов и недели; пауза
  при окончании лимита до времени сброса.
- Отказ от вызова без `structured_output` считается сбоем.
- Слой `gateway` спрятан за интерфейсом: при смене правил Anthropic можно
  переключиться на API без изменений в остальном коде (ADR-001).

### 7.5 Профи-MCP

**Инструменты** (`profi.*`): `session_health`, `list_feed`, `get_order`,
`list_chats`, `read_chat`, `submit_bid`, `send_message`, `backfill_chats`.
Изменяющие инструменты принимают ключ от повтора и разрешение ядра.

**События** (узел → ядро): `order_seen`, `order_changed`,
`client_message`, `client_typing`, `client_read`, `chat_closed`,
`session_dead`, `profile_banned`, `layout_changed`, `balance_changed`.

**Движок:** живая вкладка на аккаунт; глаза 1: события `window.__RTP`;
глаза 2: данные из ответов сайта; глаза 3: разметка; руки: клики и набор
текста, очередь команд, бережный режим, проверка экраном после действия.

**Калибровка (первое, что делается в M1):** узел на своей сессии
записывает события и ответы сайта при обычной работе; из записей
собираются схемы и тестовые образцы. Второй браузер с той же сессией
запрещён.

### 7.6 Разум

Репозиторий `sara-mind`:

```
mind/
  shared/                 # общее для Hance
    knowledge/*.md        # факты, услуги, цены, кейсы
    understanding/*.md    # типы вопросов
    speech/portrait.md    # портрет речи
    speech/examples/*.md  # образцы Бориса (обезличенные)
    judgment/*.md         # конституция, процедуры этапов
  directions/<id>/        # то же для направления
  proposals/              # черновики учителя, до «да» Бориса
```

Каждая запись: поля сверху (тип, статус, версия, источники, область,
действует с, до) и текст. Подтверждение Бориса это коммит. Индекс
обновляется после коммита.

### 7.7 Обучение

Источники: работа (правки), тренажёр, история Профи.ру. Всё проходит
через карточки «Запомнить?», затем в разум. Учитель ночью, экзамен перед
выкладкой, генератор для поиска дыр. Подробно: дизайн v3, раздел 8.

### 7.8 Направления и маршрутизатор

Система оценки: обязательные условия (проходит или нет), критерии с
весами, балл 0-100, обоснование, уверенность. Маршрутизатор выбирает
направление с выполненными условиями и лучшим баллом; два подходящих дают
одну карточку с выбором. Калибровка: 20 заявок, согласие от 85%.

### 7.9 Движок правил

| Правило | Где применяется |
|---|---|
| Пауза «Пишет клиентам» | любая отправка клиенту |
| Пауза «Тратит деньги» и пауза аккаунта | отклики |
| Деньги: кошелёк, лимиты, потолок, «да» или правило направления | отклики |
| Владелец клиента | ответы клиенту |
| Самостоятельность по теме | ответы клиенту |
| Тихие часы | напоминания, ответы не по срочному |
| Бережный режим аккаунта | любые действия на площадке |
| Сессия жива, профиль не заблокирован | любые действия на площадке |

### 7.10 Исходящая очередь

Запись намерения с ключом от повтора → выполнение через Профи-MCP →
проверка экраном → отметка. При сбое связи повтор только после проверки,
что действие не выполнено.

### 7.11 Уведомления

Шесть видов: заявка, черновик, клиент написал (если клиент у Бориса),
встреча, срочно, сводки. Кнопки передают номер задачи; ответ Бориса на
уведомление привязан к нему. Ночью без звука.

### 7.12 Пульт

Информационная архитектура по OOUX: вещи (Аккаунт, Направление, Заявка,
Клиент, Сообщение, Встреча, Задача, Знание, Урок, Тренировка, Экзамен),
связи с числом, действия, атрибуты: дизайн v3, раздел 16. API пульта:
ресурсы по вещам, живые обновления через SSE, вход по паролю и через
подпись Telegram.

### 7.13 Мастер запуска

9 шагов: дизайн v3, раздел 19; требования FR-SET.

|---|---|---|

| Сессия Профи.ру | Борис | узел Профи.ру, зашифрованно |

### 8.2 Где хранить **[П]**

Закон о персональных данных (ст. 18 ч. 5): данные граждан России при
сборе сначала записываются в базу в России; потом копию можно передать за
рубеж по правилам ст. 12 с уведомлением Роскомнадзора. Штраф за нарушение
для юрлица и ИП 1-6 млн ₽, повторно 6-18 млн ₽.

Решение: **узел Профи.ру в России делает первичную запись** всего, что
приходит с площадки (он и так первым получает эти данные), **затем
реплицирует в базу ядра за рубежом**, где работает Сара и вызывается
Claude. Ядру и Claude это ничем не мешает. Борис подаёт в Роскомнадзор
уведомление об обработке и о трансграничной передаче (разово). Перед
запуском рекомендована короткая консультация юриста.

### 8.3 Сроки и обезличивание

- Переписка закрытых клиентов хранится 2 года **[П]**, затем удаляется.
- Телефон удаляется через 30 дней после встречи **[П]**.
- В разум и тренажёр попадают только обезличенные тексты.
- Удаление по просьбе клиента: одной командой из пульта.

## 9. Безопасность

| Угроза | Мера |
|---|---|
| Ловушка в сообщении клиента («забудь инструкции») | роли без инструментов, ответ по схеме, действие решает код |
| Утечка секретов | sops и age, права 600, не в репозитории, смена при переезде |
| Захват пульта | пароль, вход через подпись Telegram только для Бориса, ограничение попыток |
| Подмена команд в Telegram | принимаются только от чата Бориса |
| Двойная трата | ключ от повтора, проверка экраном, лимиты |
| Блокировка аккаунта | бережный режим, действия через интерфейс, отдельный IP, тревога сразу |
| Потеря данных | непрерывный архив, проверка восстановления раз в неделю |
| Сара правит код в проде | у ролей нет доступа к файлам кода и командам |

## 10. Надёжность и эксплуатация

- **Цели:** NFR-REL.
- **Режимы деградации:** нет Claude: готовые тексты и черновики позже;
  нет площадки: ожидание и одно 🌐; нет Telegram: очередь уведомлений;
  нет связи между узлами: очередь команд и досылка событий.
- **Сбои и реакции:** дизайн v3, раздел 20.2 (25 случаев).
- **Бэкапы:** непрерывный архив Postgres, ежедневный снимок, проверка
  восстановления раз в неделю автоматически, разум в git дважды (сервер и
  GitHub).
- **Инструкции на случай сбоя (runbook)** для: разлогин, блокировка,
  лимит, смена сайта, восстановление базы, откат версии.

| Метрики | время заявка → карточка, «да» → отклик, клиент → ответ; доля без Бориса; лимит; ошибки по классам |
| Тревоги Борису | только то, что требует его действия (разлогин, блокировка, деньги, лимит) |
| Тревоги разработке | ошибки по классам в GlitchTip, отставание очередей, свежесть бэкапа, последнее событие площадки |

## 12. Качество и тестирование

| Уровень | Что проверяет | Когда |
|---|---|---|
| Модульные тесты | домен, правила, машина состояний, разбор данных | на каждом изменении, CI |
| Тесты на образцах | разбор событий и страниц Профи.ру по записям калибровки | CI |
| Фальшивый Профи.ру | весь путь заявка → отклик → разговор без площадки | CI |
| Экзамен | поведение Сары на 60 сценариях | перед выкладкой, на сервере |
| Слепой тест | голос Бориса | раз в неделю |
| Режим тени | всё на живой площадке без отправки | M1-M7 |

**Выход из режима тени** (условия переключения с v1):
- 7 дней подряд все сообщения клиентов замечены меньше чем за 60 секунд;
- 0 действий при неуверенном авторе;
- черновики Сары совпадают с решениями Бориса не хуже 80% по экзамену;
- карточки заявок приходят меньше чем за 2 минуты у 90%;
- Борис подтвердил переключение.

## 13. Процесс разработки

### 13.1 Где живёт код

- GitHub-аккаунт Бориса: на этом Маке уже выполнен вход
  `perpetumxcompany-alt`.
- Два приватных репозитория **[П]**:
  - `sara`: весь код (ядро, бот, пульт, Профи-MCP), документы,
    инфраструктура, тесты;
  - `sara-mind`: разум Сары; отдельно, потому что меняется каждый день
    после «да» Бориса и откатывается независимо от кода.
- Структура `sara`:

```
apps/core        ядро и бот
apps/web         пульт и Mini App
apps/profi-node  Профи-MCP и браузеры
packages/shared  общие типы и схемы
roles/           инструкции ролей и схемы ответов
infra/           docker compose, конфигурация серверов, бэкапы
docs/            спецификация, ADR, планы, документ передачи дел, справка
tests/           фальшивый Профи.ру, образцы, экзамен
```

### 13.2 Как идёт работа

```
веха → план (задачи с критериями) → ветка на задачу → тесты первыми →
код → пул-реквест → CI (тесты, типы, сборка) → проверка кода →
слияние в main → выкладка в тень → приёмка Борисом → выкладка в работу
```

- **Ветки:** `main` защищена, изменения только через пул-реквест с
  зелёным CI.
- **CI** (GitHub Actions): тесты, проверка типов, сборка образов в GitHub
  Container Registry. Экзамен с моделью запускается на сервере, а не в
  GitHub: токен подписки остаётся на нашем сервере.
- **Выкладка:** сервер сам забирает образ нужной версии и перезапускает
  службы; откат одной командой на прошлую версию.
- **Окружения:** локальное (Мак, фальшивый Профи.ру), тень (серверы,
  живая площадка без отправки), работа.
- **Секреты:** в зашифрованных файлах (sops) и на серверах, никогда в
  открытом виде в репозитории.
- **Задачи:** GitHub Project с вехами M0-M8, каждая задача плана это
  issue.
- **Решения:** каждое архитектурное решение записывается как ADR в
  `docs/adr/`.
- **Документ передачи дел** обновляется после каждого блока работы.

### 13.3 Кто что делает

| Борис | Сара (сессии Claude Code) |
|---|---|
| решения, отмеченные **[Б]** и **[П]** | планы, код, тесты, документы |
| GitHub, серверы, бот, подписка, вход на Профи.ру | настройка серверов по инструкции, выкладка |
| приёмка каждой вехи по критериям | проверка кода, экзамены, отчёт о вехе |
| интервью и тренировки для разума | подготовка тренировок и карточек |

### 13.4 Готово, когда (Definition of Done)

Задача готова, если: требования с её номерами выполнены и проверены
тестом; закрыт чек-лист аспектов (дизайн v3, раздел 22); CI зелёный;
проверка кода пройдена; документы и справка обновлены; изменения
поведения прошли экзамен.

## 14. Бот, серверы, подписка

- **Бот:** новый **[П]** (ADR-010). Создаётся в мастере запуска за 2
  минуты. v1 продолжает работать на старом боте до переключения: два
  приложения не могут читать одного бота одновременно.
- **Серверы:** не нужны для M0 (разработка на Маке). Узел Профи.ру нужен
  с начала M1 (калибровка на живой сессии), узел ядра с M2 (режим тени).
  Текущий сервер v1 работает до переключения в M7.
- **Подписка:** отдельная подписка для Сары **[П]**, чтобы её лимит не
  зависел от работы Бориса с Лорой и разработкой.

## 15. Переезд с v1

1. M1-M6: новая Сара в тени на новых серверах и новом боте, v1 работает
   как сейчас.
2. Перенос данных из базы v1: заявки, решения, траты, оценки; переписка
   выгружается заново с площадки.
3. M7: переключение по частям (лента и отклики, затем разговоры), в
   каждый момент клиентам пишет одна Сара; v1 выключается флагом и
   остаётся на сервере до конца месяца для отката.
4. После переключения: 9 старых эскалаций закрываются одним решением
   Бориса; v1, v2 и копии с секретами уходят в архив, секреты меняются.

## 18. Архитектурные решения (ADR)

| № | Решение | Почему | Отвергнуто |
|---|---|---|---|
| ADR-001 | Модель через Claude Code CLI по подписке **[Б]** | без оплаты токенов; официальный инструмент | API по ключу: платно |
| ADR-002 | Профи.ру гибридно: события и данные читать, интерфейсом действовать, экраном проверять | Профи.ру сам решает, кому показывать; нужен вид живого специалиста | только экран: медленно; прямые запросы: риск аккаунта; API приложения: защита и риск |
| ADR-003 | Профи-MCP как единственная граница площадки | один владелец браузера, понятные инструменты, тесты | доступ к браузеру из разных мест: убил сессию 29.09 |
| ADR-004 | Два узла, отдельный IP на аккаунт, а не сервер на аккаунт **[П]** | Claude не работает из России, Профи.ру режет зарубежные IP; изоляция аккаунта это профиль и IP | один сервер: конфликт стран; сервер на аккаунт: дорого без пользы; прокси: дорого и ненадёжно |
| ADR-005 | Первичная запись в России, рабочая копия за рубежом **[П]** | закон о локализации и удобство работы с Claude одновременно | всё за рубежом: риск штрафа; всё в России: Claude недоступен |
| ADR-006 | Postgres, журнал событий, DBOS | надёжность, история, устойчивые процессы без отдельного сервера | SQLite: одна запись за раз; Temporal: тяжело |
| ADR-007 | Разум как git-репозиторий файлов плюс индекс | версии, откат, нативно для Claude Code | только таблицы: хуже история; отдельный граф: избыточно |
| ADR-008 | Обучение без дообучения модели | дообучать Claude нельзя; разум, образцы, экзамены дают эффект | своя модель: дорого и слабее |
| ADR-009 | Направления и маршрутизатор **[Б]** | аккаунты разного характера без конкуренции | одна оценка на всех: аккаунты мешают друг другу |
| ADR-010 | Новый бот Telegram **[П]** | v1 работает на старом до переключения; чистое меню и Mini App | тот же бот: конфликт двух приложений |
| ADR-011 | TypeScript-монорепозиторий, React для пульта и Mini App | один язык, общие типы, наработки v1 | разные языки: дороже сопровождать |
| ADR-012 | Без календаря в первой версии **[Б]** | встречу отмечает Борис | Google Calendar: не нужен сейчас |
| ADR-013 | Интерфейс по OOUX | связи между разделами понятны без объяснений | экраны без карты: путаница |

## 20. Словарь

| Слово | Значение |
|---|---|
| Направление | характер аккаунта: какие заявки берёт, как оценивает, как откликается |
| Система оценки | правила, по которым заявка получает балл и проходит или нет |

| ADR | запись архитектурного решения: что решили, почему, что отвергли |
| C4 | способ описывать систему уровнями: контекст, контейнеры, компоненты |
