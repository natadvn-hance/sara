# M1 «Профи-MCP»: план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Служба Профи-MCP на сервере за рубежом держит живую вкладку аккаунта со своим IP, видит новые заявки и сообщения клиентов меньше чем за минуту, доставляет их ядру без потерь и дублей, сама замечает разлогин и пропажу связи; 48 часов тени это подтверждают отчётом.

**Architecture:** Веха в двух частях. **Часть A (Мак, задачи 1-12)** строит движок без живой площадки: схема `node`, исходящая очередь C8, браузер аккаунта с замком и SOCKS, живой экран для входа, глаза (события `__RTP`, ответы сайта, разметка) с подменяемыми разборщиками, сторож сессии и связи, инструменты чтения C2, образы и выкладка. Всё проверяется на «подставном сайте» (локальная копия поведения Профи.ру, ADR-017). **Часть B (сервер, задачи 13-17)** начинается только после ворот Бориса (ниже): выкладка, проверка совместной работы с v1, 48 часов калибровки, настоящие разборщики по записанным образцам, 48 часов тени и отчёт.

**Tech Stack:** то, что уже в M0, плюс Playwright (Chromium) в службе, CDP screencast для живого экрана, `@fastify/websocket`, microsocks (SOCKS на отдельный IP), Caddy, wal-g, образ `mcr.microsoft.com/playwright`.

**Spec:** `docs/spec/2026-10-22-sara-spec-v1.md` (7.5, FR-SET-4, FR-ACC-1, FR-ACC-6, FR-LEAD-1, FR-CONV-1, FR-CONV-2, FR-OPS-2), `docs/product/backlog.md` (ST-M1-01..12), `docs/architecture/contracts.md` (C2, C8), `docs/architecture/data-dictionary.md` (схема `node`, сроки), `docs/architecture/deployment.md`, `docs/architecture/threat-model.md` (T2-T5), `docs/ux/user-flows.md` (F2, F8), ADR-002, ADR-003, ADR-017, ADR-019, ADR-021, ADR-022, `docs/ops/slo.md`.

## Ворота перед частью B (решает Борис)

| № | Что | Почему |
|---|---|---|
| В1 | Сервер за рубежом, отдельный от v1: 2-4 ядра, 4-8 ГБ, 60 ГБ, основной IPv4 плюс один IPv4 для аккаунта; доступ по SSH-ключу | ADR-021; на сервере v1 новая Сара мешала бы старой, которая сейчас приносит заявки |
| В2 | Хранилище бэкапов S3 у другого провайдера | данные клиентов появляются на сервере с первого входа |
| В3 | Юрист по 152-ФЗ или явное «идём без него» | ADR-022: «консультация юриста до M1» |
| В4 | «Да» на пробу совместной работы с v1 в тихое время, Борис рядом | риск «две сессии одного аккаунта выбивают друг друга» (реестр рисков); если v1 разлогинит, ей нужен `npm run login` на Маке |

## Global Constraints

- Всё из Global Constraints плана M0 действует (язык, тире, деньги, тесты с номером требования, коммиты, `pnpm test` быстрее 5 минут).
- Тесты, CI и Мак никогда не ходят на живой Профи.ру; живой площадки касается только служба на сервере (ADR-017).
- Профиль браузера v1 (`playwright-profile/` в старой папке и на сервере v1) не открывается никогда и ничем.
- Один браузер на аккаунт: второй запуск с тем же профилем отказывает (ADR-003, случай 29.09.2026).
- В M1 служба ничего не меняет на площадке: `submit_bid` и `send_message` отвечают ошибкой `INTERNAL` «откликов в M1 нет»; присутствие и чтение только.
- Сырые данные площадки пишутся только в схему `node`; в журнал ядра уходят разобранные события без имени и текста клиента (C8, ADR-022).
- Служба Профи-MCP слушает только внутреннюю сеть Docker; наружу открыт только Caddy на 443 (T4).
- Браузер аккаунта выходит в сеть только через SOCKS своего IP; IP вкладки сверяется с IP аккаунта, при расхождении аккаунт стоит (FR-ACC-1).
- Пороги: новая заявка у 90% меньше 60 с, сообщение у 95% меньше 60 с (FR-LEAD-1, FR-CONV-1, SLO-3); страховка: лента раз в 60 с, чаты раз в 10 минут; нет связи: проверка раз в 5 минут, одно 🌐 после 30 минут, одно «связь вернулась» (ADR-021, как v1).
- Автор каждого сообщения: `client`, `specialist`, `system` или `unknown`; при `unknown` действий по чату нет, событие `profi.author_unclear` (FR-CONV-2, T2).
- Сырые записи `node.raw_*` живут 30 дней, подтверждённые строки очереди 7 дней (data-dictionary, раздел 4).

## Review Focus

1. **Второй браузер на тот же профиль** (перезапуск контейнера, пока старый процесс ещё жив): второй запуск отказывает с `SECOND_BROWSER`, первый продолжает работать. Тест в Task 5.
2. **Разметка или формат ответов поменялись** (разборщик ничего не узнаёт, страница жива): служба не молчит как «новых заявок нет», а через 10 минут без единого разобранного сигнала шлёт одно `profi.layout_changed`, «Состояние системы» показывает «глаза не видят». Тест в Task 9.
3. **Одна заявка или сообщение пришли тремя путями** (событие, ответ сайта и страховка): одно событие ядру, по номеру площадки. Тест в Task 9.
4. **Ядро лежит часами или служба перезапускается посреди очереди**: события копятся в `node.outbox_node`, после возврата уходят по порядку и по одному разу. Тест в Task 3.
5. **Сессия умерла, пока Бориса нет рядом**: одно 🚨, без повторов каждую минуту; после входа одно 🟢 и сверка пропущенного за время простоя. Тест в Task 8.
